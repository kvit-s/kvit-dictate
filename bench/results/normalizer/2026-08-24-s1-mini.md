# s1-mini — do-no-harm run, 2026-08-24

Produced by `bench/normalize.py` against `http://strixhalo.lan:10301/v1/text/normalize`.
Aggregates and the damage cases only; the per-case JSON contains model output and stays out of
history under the `bench/results/**` rule (plan.md §1.9).

**Quantisation: not recorded.** The run was taken with `--quant unknown`, so it cannot be
compared against the model card's 94.8% token accuracy, which was measured on `Q4_K_M`. Re-run
with `--quant` set before quoting either number next to the other.

## What was measured

The 83 prompts in `bench/prompts/{tech,hard}.jsonl` that carry a transcript, sent as-is. The
eight `ambient` prompts are excluded: their `text` is empty because they are recording prompts
for a silent or noisy room, and there is nothing there for a text model to damage.

This is a **damage** test, not a quality test. The prompts are already correct written text, so a
normalizer that does no harm changes almost nothing. It says nothing about whether the model's
cleanups are any good — that needs the paired raw-transcript/intended-text corpus this
repository does not yet have.

| guard rejections | 5 (6.0%) |

`hard`'s WER cannot be read as a quality signal in either direction. Those references are
verbatim-as-spoken by construction — `hard-001` says "Reference is verbatim as spoken, including
the correction", `hard-002` says "Do not clean it up" — so a *correct* normalisation scores as
error against them.

## The three damaged prompts

    tech-001  llama.cpp
      in   Rebuild llama.cpp with --n-gpu-layers 35 and see whether the RTX 5090 keeps up.
      out  Rebuild LLMCpp with --n-gpu-layers 35 and see whether the RTX 5090 keeps up.

    tech-002  sm_120
      in   CUDA sm_120 kernels are compiled in, so Blackwell needs no PTX JIT fallback.
      out  CUDA SM120 kernels are compiled in, so Blackwell needs no PTX JIT fallback.

    hard-003  ONNX
      in   Run the ONNX export first and then, hmm, actually run the int8 quantisation first.
      out  Run the int8 quantisation first.

The first two are the finding. `bench/metrics.py:675` listed `"sm 120"` as a known-bad rendering
of `sm_120` before this model existed, and the model produced `SM120` — the same failure, a
spelling the table had not thought of. `LLMCpp` is worse than a mis-rendering: it is a rename of
a real identifier into one that does not exist, which is the failure mode a rewriter has and a
recogniser does not.

**The third is a false positive, and it matters.** `hard-003` is the model doing exactly its job:
the speaker abandoned the ONNX clause and landed on int8, and the rewrite resolves the false
start correctly. `ONNX` vanished because the clause containing it was the one the speaker took
back. The guard cannot tell that apart from damage, so it rejects a correct rewrite. Every
protected term that appears only inside an abandoned clause will do this.

## What this says about the guard

It works: `src/normalizer.cpp`'s guard rejects all three, and in every case the user keeps the
text as spoken. `llama.cpp` and `sm_120` never reach a document.

The cost is the 6.0% rejection rate, of which at least one in three is a correct rewrite thrown
away. That is the number to watch — the feature is only worth having while the great majority of
cleanups survive the guard, and a model that has to be overruled often is one whose cleanups
mostly never reach the user.

## Not yet answered

* Whether `Q4_K_M` behaves the same. The card's accuracy figure is for that build; this run is not.
* Whether feeding `context.terms` to the endpoint's `context` control prevents the `llama.cpp`
  and `sm_120` damage. If it does, the term list stops being only a veto and starts being a fix.
* Whether the 0.5 length floor in `guard_verdict` is right. Three of the five rejections here
  were `RejectTooShort`, and `hard-021` ("sixty five thousand five hundred and thirty six" →
  "65,536") is correct ITN that the floor rejected purely for shortening the text.
